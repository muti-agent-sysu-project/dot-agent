本文档如实记录本次会话中遇到的全部错误、根因与修正方式，供日后排查与答辩问答参考。

## 一、代码评审发现并修复的 4 个 bug（提交 7147fa2）

### 1. θ 自适应的消融污染（严重度：高，影响论文数据）

- **现象**：`ThetaAdapter.apply_to` 不检查 `enabled` 开关。只要存在上次自适应运行落盘的
  `config/router_theta_adaptive.json`，即使本次以 `DOT_ADAPTIVE=off` 启动，
  executor 每步都会把旧自适应 θ 覆盖写进 router。
- **后果**：消融对照组（关自适应）实际上被旧状态污染，论文里的对照数据失真。
- **修复**：`apply_to` 入口 `if not self.enabled: return`，关闭时绝不触碰 router。
- **教训**：带持久化状态的开关型模块，"关闭"必须等价于"该模块不存在"，
  不能只是"不再学习"。恢复旧状态的代码路径与开关是两条独立的线，要分别审。

### 2. 判别编号两位数误解析（严重度：中，静默出错）

- **现象**：`parse_judge_reply` 的编号正则 `([1-9])` 无数字边界，云端回 "42"
  被解析成候选 4、"12" 变候选 1。
- **后果**：静默选错候选，不报错、难发现。
- **修复**：正则加 `(?<!\d)(?!\d)` 边界；两位数直接判解析失败，走降级路径。
- **教训**：解析模型自由文本输出时，正则要假设最坏情况；"能匹配"和"匹配对"是两回事。

### 3. judge 回填校验误报（严重度：中，污染第四指标）

- **现象**：判别路径 `restore(picked, original=candidates[0])` 用候选 0 做实体数
  守恒对比。但判别输出可能是"修正"而非候选复述，对比必然溢出。
- **后果**：`roundtrip_failures`（论文第四指标"披露"的一部分）被虚假抬高。
- **修复**：判别路径传 `original=""`，保留假名残留检查、跳过溢出检查（不适用）。
- **教训**：校验逻辑复用时，要检查"这个校验对新的输入形态是否仍然成立"。

### 4. 坏记录拖垮全部查询（严重度：中，可用性）

- **现象**：`records.py` 的 `list()`/`export_csv()` 对记录字段直接下标取值。
- **后果**：任何一条旧格式/损坏记录缺字段 → KeyError → 列表页、统计、导出全挂。
- **修复**：全部改 `.get` 容错；补回归测试（手工写入缺字段坏记录）。
- **教训**：列表类接口必须容忍单条脏数据；"一条坏，全部崩"是典型的容错缺失。

## 二、部署过程中的错误时间线

### 错误 1：ModelScope 仓库名猜错

- **做了什么**：直接猜 `Qwen/Qwen3-4B-Instruct-2507-GGUF` 发起下载。
- **结果**：0 字节 + `Resource does not exist`。
- **正确做法**：先查 `/repo/files` API 确认仓库与文件名（实际是 `Qwen/Qwen3-4B-GGUF`）。
- **教训**：下载前先验证资源存在性，不要凭记忆写仓库名。

### 错误 2：GitHub clone 被墙断（两次）

- **现象**：学术加速下 `git clone --depth 1` 报 `curl 18 transfer closed`。
- **处理**：gitee 镜像又要求认证（仓库不存在）；最终改从 release 下载压缩包。
- **教训**：AutoDL 学术加速对 GitHub 大对象传输不稳定，重仓库考虑镜像站或
  release tarball，并始终用断点续传（`wget -c`）。

### 错误 3：nvcc 不在 PATH → cmake 配置失败

- **现象**：`CMakeCUDACompilerId.cu failed`。
- **根因**：nohup 后台脚本没继承 `source /etc/network_turbo` 会话里的环境，
  `/usr/local/cuda/bin` 不在 PATH。
- **教训**：后台脚本要自带完整环境（显式 `export PATH=/usr/local/cuda/bin:$PATH`），
  不要依赖交互 shell 的状态。

### 错误 4：CUDA 11.8 缺 PDL API → 编译失败

- **现象**：`cudaGridDependencySynchronize is undefined`（最新 master 用了
  CUDA 12 的 programmatic dependent launch）。
- **修复**：给 `common.cuh` 打补丁，`CUDART_VERSION < 12000` 时提供
  `__device__ __forceinline__` 空实现（PDL 只是启动优化，功能无损）。
- **附加坑**：第一版补丁用 `static inline`（host 限定），device 代码调用会报错，
  改为 `__device__` 限定符后才通过。

### 错误 5：NCCL 头文件过旧

- **现象**：`ncclConfig_v21400 has no member maxCTAs`。
- **修复**：`-DGGML_CUDA_NCCL=OFF`（单机推理用不到 NCCL）。

### 错误 6：并发 80 导致编译竞态

- **现象**：`opening dependency file ... .o.d: No such file or directory` 等
  随机错误（内存磁盘都充足，纯竞态）。
- **修复**：降到 `-j16` 稳定；后期进度慢又提回 `--parallel 48`（增量编译）。
- **教训**：nvcc 并发不是越大越好；make 增量特性可以随时调整并发不丢进度。

### 错误 7：误用根 Makefile

- **现象**：`make -j16` 报 "The Makefile build has been replaced by CMake"。
- **修复**：`cmake --build build --parallel 48`。

### 错误 8：pkill 误杀自身 SSH 会话（出现 3 次）

- **现象**：`pkill -f "cmake --build"` 的模式匹配到了 SSH 命令行自身，
  会话被杀，后续命令没执行（exit 255）。
- **后果**：多次修改没落地（start-llama.sh 路径改写丢失、sed 没打上、
  build.status 无人写入），造成"命令执行了但没生效"的假象。
- **教训**：
  - 远程清理进程用精确 PID（`pgrep` 结果逐个 kill），不用宽模式 `pkill -f`；
  - 关键修改（写文件、sed）要立即回读验证，不能假设命令链完整执行。

### 错误 9：下载预编译包前没查目标机 glibc（最大的弯路）

- **时间成本**：约 40 分钟（用户帮忙下载 774MB + 传输）。
- **现象**：官方预编译包要 `GLIBC_2.38`，AutoDL 镜像是 Ubuntu 22.04（2.35）。
- **应该先做**：下载任何二进制分发前，先 `ldd --version` / `ldd binary` 核对
  动态链接要求。预编译包是"构建机环境的函数"，不是通用产物。
- **正确路径**：源码编译（在目标机上编译天然匹配本地 glibc）。
- **教训**：二进制兼容性检查（glibc/CUDA driver/ABI）应在下载前完成，
  一条命令的事，省一小时的传输。

### 错误 10：GitHub 下载绕路太久，没及时求助用户

- **现象**：学术加速 + ghproxy 都只有 160KB/s 且频繁断流，
  单方面反复重试了约 40 分钟。
- **正确做法**：早一点把直链给用户（用户的网络更快），
  或早一点改用"本机下载 → scp 直传"（实测 4MB/s）。
- **教训**：网络瓶颈不在解决路径上死磕，及时换通道、及时向有更好通道的人求助。

### 错误 11：Qwen3 默认思考模式吃掉短预算

- **现象**：max_tokens=8 的测试请求返回空 content（token 全花在 reasoning）。
- **尝试**：`--reasoning-budget 0` 无效（思考文本仍漏进 content）。
- **修复**：`--reasoning off --jinja`（即交接文档里的 `-rea off`）。
- **教训**：交接文档里的启动参数是有原因的，迁移时逐条对照而不是重新发明。

### 错误 12：GLM-5.3-flash 始终思考，两层适配

- **现象 A**：预热 max_tokens=32，思考耗尽预算 → content 为空 →
  `model_incomplete_answer` → 服务退出（DOT_REQUIRE_REAL=1 预热即失败）。
- **现象 B**：`CLOUD_THINKING=disabled` → GLM 返回 HTTP 400
  （code 1210："该模型始终思考，不支持关闭思考"）。
- **修复**：`CLOUD_THINKING=enabled` + 预算提到 256；正式请求预算提到 2048
  （`DOT_BUDGET_CLOUD_ANSWER`），缓解思考型模型偶发截断。
- **教训**：换云端模型时先读它的 API 行为说明（是否强制思考、参数取值），
  再设网关参数；`finish_reason=length` 的重试/失败语义要按模型特性调预算。

### 错误 13：验证用例构造不当（两条，非代码错误）

- **现象 A**：敏感查询里手机号没被分解进子任务描述，云端没收到任何实体，
  走了 CLOUD_PLAIN——隐私面板全 0，看起来"假名化没工作"，实际是
  依赖图传播的正确行为（敏感实体根本不需要出域）。
- **现象 B**：构造"难题"想触发云端升级，但 Qwen3 对该题一致性 1.0、
  难度分 0.33/0.00，过不了 θ=0.5——路由不出云端，测试无效。
- **正确做法**：功能级验证用内部接口直接构造（`theta_overrides={REASONING: 0.01}` +
  数字必须进子任务的查询），不要期望自然流量恰好命中每个分支。
- **教训**：测试分支覆盖要主动构造，"随便发一条看看"验证不了条件路径。

## 三、通用教训清单

1. **兼容性前置检查**：glibc / CUDA driver / API 行为，任何二进制或外部服务，
   下载和接入前先核对，一条命令省一小时。
2. **后台脚本环境自包含**：PATH、代理、密钥全部显式写进脚本，不依赖会话状态。
3. **远程操作可验证**：每步修改后立即回读确认；宽模式 pkill 会误杀自己的会话。
4. **开关即隔离**：带持久化状态的模块，关闭必须等价于不存在（消融数据可信的前提）。
5. **分支覆盖靠构造**：路由/隐私这类条件路径的验证，用内部接口直接设定前提条件。
6. **网络瓶颈及时换通道**：单通道反复重试超过 10 分钟就该换路或求助。
